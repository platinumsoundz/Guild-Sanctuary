# The Sanctuary — beta testing guide

Thank you for helping shape The Sanctuary. The beta is a work in progress; some screens are working features and some are clearly labelled previews or concepts.

## What to test first

1. **Today:** Does the purpose of the platform make sense within 10 seconds?
2. **Community:** Can you find the feed and understand how to read or share a post?
3. **People & discovery:** Is it clear how to find a profile?
4. **Messages, events, and notifications:** Can you tell what is implemented and what remains a preview?
5. **Feature concepts:** Do Circles, Practice Library, Daily Reflection, and Self-discovery make sense? What would you change?
6. **Mobile use:** Try one-handed navigation, scrolling, text entry, and closing dialogs.
7. **Accessibility:** Try keyboard navigation on desktop, zoom text, and check whether button labels are understandable.

## Start with the Today tour

The Today screen includes an optional six-step checklist. Use it to explore the community, discover people, open a concept preview, browse feature statuses, prepare feedback, and visit the product map. The completion count is stored in this browser only; it is not a public score or an account-wide record. You can reset it at any time. If browser storage is unavailable, progress may only last for the current session.

The Build Radar section is a directional snapshot, not a promise of release dates. The concept preference picker is also local-only; it does not count or transmit votes. If you want to share your choice, add it to a feedback report and send the report yourself. Always use each feature card's status label to distinguish an existing route from a preview or concept.

## How to report a bug

Please include:
- **Where:** the screen or feature name.
- **Steps:** what you clicked or typed, in order.
- **Expected:** what you thought should happen.
- **Actual:** what happened instead.
- **Device/browser:** for example, Android + Chrome.
- **Screenshot or screen recording:** only if it helps and contains no private information.

One issue per report is best. If something looks unfinished but is clearly labelled as a concept, that is product feedback rather than necessarily a bug.

## How to give feature feedback

Try to answer one or two:
- What would make this useful to you?
- What feels confusing or unnecessary?
- What would you expect to happen when you press the main button?
- Would you use this alone, with friends, or in a small group?
- Is any wording or information too personal, unclear, or hard to find?

The Today page has a beta feedback form that formats a report for you to copy. It does not submit anything to a server; share the copied report with the project owner or paste it into a GitHub issue.

## Status labels

- **Available** — a route exists and can be explored.
- **In preview** — a partial interface exists; do not assume all integrations are complete.
- **In design** — a clickable concept shows intended direction; it is not a live feature.
- **Safety gated** — visible for transparency, but intentionally not enabled for real transactions or sensitive actions.

## Privacy

Do not include passwords, verification codes, private messages, personal medical details, payment details, or other sensitive information in feedback. Use fictional examples when testing. If a screen shows information that should not be visible to you, stop and report only the minimum details needed to investigate.

## What happens next

Feedback is triaged into:
- **Bug:** something that should work is broken.
- **Usability:** a real feature is hard to understand or use.
- **Product idea:** a proposed new behavior or feature.
- **Release blocker:** a problem that makes a release unsafe or unreliable.

The team will prioritise issues by user impact, frequency, severity, and effort. Reporting an issue does not guarantee it will be shipped, but it gives the team concrete evidence for a decision.
